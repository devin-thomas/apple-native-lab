# Contributing

A useful contribution begins with a user-visible moment, not a framework import. Propose one interaction that becomes meaningfully better because the implementation is native. Explain the device requirement, the ordinary/manual equivalent, and the limitation the demo will teach.

Use [EXPERIMENT_TEMPLATE](docs/EXPERIMENT_TEMPLATE.md). Add one implementation ticket and one qualification ticket. Provide original fixtures, accessibility behavior, a reset path, and a source/availability record. An unsupported device must not encounter a crashing or unexplained dead end.

Keep optional entitlements, model packages, accessories, and external services isolated. Do not add a dependency to the core without a recorded rationale and license inventory. No contribution may require access to a maintainer's account or private repository.

Pull requests should identify actual tests run, simulated tests, and untested hardware separately. An elegant failure explanation is preferable to a fabricated successful benchmark. Screenshots and videos need an original-media rights check and a metadata/privacy pass.

Experimental code can be small; architecture claims cannot be vague. Reusable components must document their input/output and lifetime contract. Preserve public behavior when extracting a component for another application.
