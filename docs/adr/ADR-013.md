# ADR-013 — Short-lived, scoped grants for destructive and external commits

Status: accepted 2026-09-29 (CORE-006).

## Decision

Hosts compose `OperationService` with `GrantAuthorizationPolicy`. A commit needs a live `CommitGrant` when it is destructive (for example Reset Demo or an archive), or when it arrives from a share extension or an authorized peer. A grant names the adapter, the operation kinds, the target, and an expiry measured on a monotonic clock: 60 seconds by default, never more than 300. Grants are issued only by an explicit user action in the app, checked inside `perform`, and fail closed when missing, expired, or out of scope.

Grants only narrow access. They sit beneath the fixed adapter ceilings of ADR-011, so no grant lets a model tool commit or lets a share extension destroy data.

## Rationale and consequences

Imported content, including text that imitates instructions or grant tokens, is data and can never create a grant or reach a commit path. A destructive action therefore always traces back to a person pressing a control moments earlier. Hosts must issue a grant as part of each confirmation flow; a missing grant is a refusal with a readable reason, not a silent failure.

The import side of the same ticket keeps file-system work in `Packages/LabStaging`, so a share extension can link staging without the SQLite store, and keeps diagnostics behind one metadata-only facade in LabDomain.

## Validation

`GrantTests`, `InstructionInjectionTests`, and `ImportAdoptionTests` in `Packages/LabDomain`, plus the LabStaging suites, cover expiry, scope, fail-closed behavior, injected instructions, and idempotent duplicate imports.
