# ADR-011 — Fixed permission ceilings per adapter kind

Status: accepted 2026-09-29 (CORE-002).

## Decision

Every request names the adapter it arrived through: app UI, App Intent, share extension, authorized peer, or model tool. Each kind has a fixed ceiling compiled into `LabDomain`:

| Adapter | Ceiling |
|---|---|
| App UI, App Intent | read, propose, commit, commit-destructive |
| Share extension, authorized peer | read, propose, commit |
| Model tool | read, propose |

An actor's effective permissions are its grants intersected with its adapter's ceiling. An injected `AuthorizationPolicy` can only narrow access further. A request ID is bound to the adapter kind and operation, so the same ID from a different adapter is refused. Every call, including a replay of a recorded request, is authorized again.

## Rationale and consequences

This makes ADR-004 (operations own authorization) and ADR-007 (AI proposes; deterministic code commits) structural rather than conventional. A model tool cannot commit anything, even non-destructively: its output reaches the store only when a person reviews a proposal and an actor allowed to commit submits it under a new request ID. Content arriving from outside the app (shared items, paired peers) cannot destroy data without the user acting in the app.

Adapter kind is trusted by wiring: code inside the app composes each adapter with its scope, and a scope is never decoded from a payload. Hosts hand adapters the service, never the store. Widening a ceiling requires a new decision record.

## Validation

`Packages/LabDomain/Tests/LabDomainTests/AuthorizationTests.swift` runs the ceiling rules for all five adapter kinds. A compile probe outside the package confirmed external code cannot construct an `AuthorizedCommit`, construct a receipt, or decode an `OperationRequest`.
