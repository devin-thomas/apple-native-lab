# ADR-018 — Commerce opens in a local simulation

Status: accepted 2026-09-30 (LAB-040-A).

## Decision

The Mac and iPhone commerce screens use the declared transaction-state fallback. They never import StoreKit or call a storefront. Original test products also have a local `Fixtures/LAB-040/Commerce.storekit` configuration for developer-only StoreKit Testing. No default scheme enables it and the loader probe requests no purchase.

Simulation history belongs to one screen session and is labeled accordingly. Lab items and receipts persist through the existing operation service; they are teaching records, never authority for a real paid feature. Reset Commerce clears only its product notes and session state, preserving unrelated records and immutable receipts. No account, network route, entitlement, or cost is introduced.

## Rationale and consequences

A default control cannot create a real charge. This implements the fallback independently of StoreKit Testing, rather than presenting a simulator as live StoreKit integration. StoreKit transactions, system refund UI, and device qualification remain separate work in LAB-040-B.

The desk stages simulator state until an authorization-checked operation commits. A stale receipt is a refusal. Multi-product restore and reset commit one product at a time; earlier successful products remain committed if a later product fails. A session admits at most 256 request IDs. Replays recheck authorization; concurrent desk actions are refused while a commit awaits its backend.

## Validation

`CommerceWithoutTricksOperationTests`, `CommerceFailureTests`, and `CommerceHostTests` cover fixture operations and the host receipt path. The completion record names the actual runs and the separate configuration-loader result. The local StoreKitTest service refused configuration on the standalone XCTest runner; this is a blocked adapter gate, not a passing configuration test. Application-hosted StoreKit Testing remains unrun.
