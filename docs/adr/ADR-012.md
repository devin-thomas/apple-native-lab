# ADR-012 — SQLite local store with fixed demo and user namespaces

Status: accepted 2026-09-29 (CORE-003). The no-items-in-demo-collections rule is provisional until LAB-001 tests it with people.

## Decision

`Packages/LabStore` persists the `OperationStore` contract in one SQLite file through the system `SQLite3` library. It adds no third-party package.

- `apply(_:)` runs the whole contract in one `BEGIN IMMEDIATE` transaction. The receipt check and every revision precondition are read while the connection holds the write lock, so another connection or process cannot write between the checks and the writes.
- The file uses write-ahead logging with `synchronous = FULL`. `PRAGMA user_version` is the schema version and `PRAGMA application_id` marks the file as the store's. Each migration is plain SQL that runs in its own transaction together with its version bump. A released step never changes. A file from a newer build, or a file that is not the store's, is refused and left unchanged.
- Every entity row has an `extras` JSON column for metadata the build does not interpret. Upserts leave it in place, and migrations carry it over unchanged.
- Entities have a namespace, `user` or `demo`, stored in the same file. An item has its collection's namespace, and namespaces never change. Everything a person creates or imports is `user`. Only Reset Demo creates `demo` entities, from the seed in `Fixtures/demo/seed.json`, and a person cannot add items to a demo collection. Schema triggers enforce these rules for any writer: a user row is never deleted, no row changes namespace, and receipts are never updated or deleted.
- Reset Demo is `DomainOperation.resetDemo(seed:)` in LabDomain, so it passes authorization like any other operation. It is destructive, so it needs `commitDestructive`, which only the app UI and App Intents can hold (ADR-011). One commit makes the demo namespace match the seed. It restores changed samples at their next revision, never back to revision 1, and removes demo entities the seed no longer lists.

## Options considered

| Need | SQLite (chosen) | Core Data | SwiftData |
|---|---|---|---|
| Idempotency and preconditions in one transaction | `BEGIN IMMEDIATE` takes the write lock before the checks | Optimistic merge conflicts detected at save; checks read before the lock | Same as Core Data, with less control over the save |
| Cross-process safety for a later App Group | File locks and WAL across processes, proven here against a separate `sqlite3` process | Works, but needs persistent history tracking to see other processes' changes | Same, with less visibility |
| Migration control | Ordered SQL steps in one transaction each, tested against a frozen v1 file | Lightweight or staged mapping models | `VersionedSchema` and migration plans |
| iOS, macOS, watchOS, tvOS | Available on all four | Available on all four | Available on all four |
| `swift test` without a host app | Yes | Yes, with a model built in code | Yes, but model macros and a container add setup |
| Opaque, unknown metadata | A JSON column the store never rewrites | Transformable attribute | Codable attribute |

Core Data and SwiftData could meet the contract. Each would need extra machinery to put the request-ID check and the revision checks inside the lock that the write takes. With SQLite, one transaction covers both.

## Rationale and consequences

The store contract (CORE-002) needs "check, then write, atomically" across processes. SQLite provides that directly, and every guarantee is testable with deterministic fault points and real files. The costs are hand-written SQL, a hand-written row mapping, and a migration file that must be kept append-only.

The architecture spec says to separate demo and user data "by namespace and storage location". This decision uses one file with a namespace column instead of two files. SQLite does not make a transaction atomic across two attached files in WAL mode. A reset or an import that spanned two files could then leave one updated and the other not after a crash, and every idempotency check would span both files. One file keeps every commit and its receipt atomic. The seed is still stored apart from user data: it is read-only data in `Fixtures/`, loaded and validated before anything is written.

Refusing items in demo collections is a decision about data loss. It guarantees that Reset Demo never removes anything a person created. Edits to sample objects are still part of the demo, and a reset reverts them. Hosts should label demo collections that way.

The trigger that forbids deleting user rows is deliberate. The planned "Delete My Imported Data" feature (SECURITY_AND_PRIVACY) will need a migration that replaces it, and that needs its own decision.

Open for later tickets: the App Group container, file protection class, and suspension behavior (CORE-006, CORE-008). `fullfsync` is off, so after sudden power loss the latest commits may be missing, but the file stays consistent.

## Validation

`swift test --package-path Packages/LabStore` covers:

- The store contract, run against both the in-memory store and SQLite.
- An interruption at every fault point of a multi-row commit.
- Recovery from a mid-transaction copy of the files, with uncommitted pages on disk.
- A migration from a frozen v1 file.
- Namespace triggers.
- A separate `sqlite3` process blocked by, and then serialized after, a commit.

`swift test --package-path Packages/LabDomain` covers Reset Demo's authorization and planning.
